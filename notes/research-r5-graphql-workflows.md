## What a gqlgen Subgraph Repo Typically Contains

Understanding the structure of a gqlgen project is essential before diving into the demo scenarios. Here's what you'll find:

### Core GraphQL Files

**Schema Definition (schema.graphql or schema.graphqls)**
- The source of truth for your GraphQL API contract
- Defines types, queries, mutations, subscriptions
- Location varies: often `graph/schema.graphql`, `schema.graphqls`, or split into `schema/*.graphql`
- gqlgen reads this to generate resolver interfaces and model types

**Generated Code (generated.go, models_gen.go)**
- Lives in `graph/generated/` or similar
- Auto-generated by `go run github.com/99designs/gqlgen generate`
- NEVER edit these files manually - they get overwritten
- Includes: resolver interfaces, model structs, execution engine

**Resolver Implementations (schema.resolvers.go)**
- Where you write the actual business logic
- Implements the generated resolver interfaces
- Typical location: `graph/schema.resolvers.go` or split by domain
- Pattern: each field resolver fetches data from backing services, databases, or other subgraphs

### Configuration Files

**gqlgen.yml or gqlgen.yaml**
- Configuration for code generation
- Specifies: schema paths, output locations, model mappings, custom scalars
- Example settings: autobind models, resolver layout (follow-schema vs single-file), directives

**go.mod and go.sum**
- Standard Go dependency management
- Key dependency: `github.com/99designs/gqlgen`
- Often includes federation libraries if this is an Apollo subgraph

### Supporting Code

**Dataloaders (optional but common)**
- Batch and cache database queries to avoid N+1 problems
- Location: `graph/dataloaders/` or `loaders/`
- Generated or hand-written depending on the team's approach

**Directives (optional)**
- Custom GraphQL directives for auth, validation, caching
- Implementation: `graph/directives/` or `directives/`
- Configured in gqlgen.yml

**Tests**
- Resolver tests: `graph/schema.resolvers_test.go`
- Integration tests: may use graphql-go or httptest
- CI typically runs: `go test ./...`, codegen check, linters

### CI/CD Artifacts

**Codegen Drift Check**
- Most teams run `gqlgen generate` in CI and fail if generated files change
- Command pattern: `go run github.com/99designs/gqlgen generate && git diff --exit-code`
- Purpose: ensures schema and resolvers stay in sync

**Docker and Deployment**
- Dockerfile, docker-compose.yml for local dev
- Kubernetes manifests or Helm charts for deployment

### Federation-Specific (If Apollo Subgraph)

**Federation Directives in Schema**
- `@key`, `@requires`, `@provides`, `@extends`, `@external`
- Defines entity boundaries and relationships between subgraphs

**Entity Resolvers**
- Special resolvers that resolve entities by key
- Pattern: `func (r *entityResolver) FindUserByID(ctx context.Context, id string) (*User, error)`


## CLAUDE.md Template for gqlgen Subgraph Projects

A well-crafted CLAUDE.md is the single most important onboarding tool for Claude Code in a gqlgen project. It answers the question: "What does Claude need to know to be productive on day one?" Here's what to include:

### Schema and Codegen Commands

```markdown
## GraphQL Schema

- **Location:** `graph/schema.graphql` (or `schema/*.graphql` if split)
- **Regenerate code:** `go run github.com/99designs/gqlgen generate`
- **CRITICAL:** Never manually edit files in `graph/generated/` - they are overwritten on every codegen run
- **CI check:** We run codegen in CI and fail if git working tree is dirty afterward
```

**Why this matters:** Claude needs to know where the schema lives and how to regenerate code. Without this, Claude might edit generated files (disaster) or run the wrong command.

### Resolver Patterns and Conventions

```markdown
## Resolver Implementation Patterns

- **Location:** `graph/schema.resolvers.go` (or split by domain in `graph/resolvers/`)
- **Pattern:** Each resolver calls a service layer function from `internal/services/`
- **Error handling:** Wrap all errors with context using `fmt.Errorf("action failed: %w", err)`
- **Authentication:** Use `auth.GetUserFromContext(ctx)` to extract current user
- **Authorization:** Check permissions before fetching data, not after
- **Dataloaders:** Use `loaders.LoaderFromContext(ctx)` to get dataloader batch functions
```

**Why this matters:** Prevents Claude from inventing patterns that don't match your codebase. If your resolvers always call a service layer, say so. If you have a specific error-wrapping convention, document it.

### Error Shape and GraphQL Errors

```markdown
## Error Handling

- **User-facing errors:** Return `gqlerror.Errorf("user-friendly message")`
- **Internal errors:** Log with `log.Error()`, return generic message to client
- **Validation errors:** Use `inputerror.New("field", "reason")` for input validation
- **Partial errors:** Resolver can return both data and error - GraphQL will include error in `errors` array
- **Error codes:** We use extensions to add error codes: `gqlerror.Errorf("...").Extensions = map[string]interface{}{"code": "NOT_FOUND"}`
```

**Why this matters:** GraphQL has unique error semantics (partial errors, extensions). Claude needs to know your team's conventions.

### Dataloader Conventions (If Applicable)

```markdown
## Dataloaders

- **Generated by:** `go generate ./loaders` (using https://github.com/vektah/dataloaden)
- **Usage pattern:** `user, err := loaders.LoaderFromContext(ctx).UserLoader.Load(userID)`
- **Batching:** All Load() calls within a single request are batched automatically
- **Context keys:** Dataloaders are attached to request context via middleware in `server/server.go`
- **Testing:** Use `loaders.NewMockLoaders()` in resolver tests
```

**Why this matters:** Dataloaders are a common source of confusion. Claude needs to know how to use them correctly and where they're configured.

### Testing Conventions

```markdown
## Testing

- **Resolver tests:** `graph/schema.resolvers_test.go` - use table-driven tests
- **Mock dependencies:** We use `mockery` to generate mocks for service layer interfaces
- **Test database:** Use `testutil.SetupDB(t)` to get a clean test database per test
- **GraphQL integration tests:** `server_test.go` - send actual GraphQL queries via httptest
- **Run tests:** `go test ./...`
- **Coverage requirement:** Minimum 80% on new resolver code
```

**Why this matters:** Claude needs to know how to run and write tests in your style. Without this, Claude might use the wrong test framework or skip tests entirely.

### CI/CD Pipeline and Check Names

```markdown
## CI Pipeline (GitHub Actions)

- **Workflow file:** `.github/workflows/test.yml`
- **Checks:**
  - `test` - runs `go test ./...`
  - `lint` - runs `golangci-lint run`
  - `codegen-check` - runs `gqlgen generate` and fails if working tree is dirty
  - `federation-check` - validates schema against rover CLI
- **Failed codegen-check:** Usually means schema was updated but generated code wasn't committed
- **Fix:** Run `go run github.com/99designs/gqlgen generate` locally and commit the changes
```

**Why this matters:** When CI fails, Claude needs to know what the check names mean and how to fix them. "codegen-check" is a common gqlgen-specific failure.

### Backing Services and Data Sources

```markdown
## Data Sources

- **Primary database:** PostgreSQL via `database/sql` and `sqlc` for queries
- **User service:** REST API at `internal/clients/userservice/` - client generated from OpenAPI spec
- **Cache:** Redis via `go-redis/redis` for session data and frequently-accessed entities
- **Federation:** This subgraph extends the User entity from the accounts subgraph
```

**Why this matters:** When adding a new field, Claude needs to know where the data lives and how to fetch it.

### Development Workflow

```markdown
## Local Development

- **Start services:** `docker-compose up -d` (starts Postgres, Redis)
- **Run server:** `go run server/server.go` (listens on http://localhost:8080)
- **GraphQL Playground:** http://localhost:8080/playground
- **Hot reload:** Use `air` for auto-restart on file changes (`air -c .air.toml`)
- **Schema changes workflow:**
  1. Edit `graph/schema.graphql`
  2. Run `go run github.com/99designs/gqlgen generate`
  3. Implement new resolver methods (gqlgen will error if you don't)
  4. Write tests
  5. Run `go test ./...`
  6. Commit schema AND generated code together
```

**Why this matters:** Claude needs to know the full workflow for making changes. This prevents partial commits or skipped steps.

### Key Architecture Decisions

```markdown
## Architecture Notes

- **Why gqlgen?** Chosen for code-first approach and strong Go typing
- **Why dataloaders?** Required to avoid N+1 queries - all resolvers that return lists must use dataloaders
- **Why service layer?** Resolvers are thin - business logic lives in `internal/services/` for reusability
- **Federation boundaries:** This subgraph owns Product, Order entities; User entity is extended from accounts subgraph
```

**Why this matters:** Helps Claude understand the "why" behind patterns, leading to better suggestions.


## Scenario B: Consumer-Driven Field Addition

**Context:** A consumer team (frontend web app) requests two new fields on the existing `Product` type: `averageRating` (Float) and `reviewCount` (Int). They need these fields to display product cards with star ratings. The data exists in a backing service (Reviews API) but isn't exposed in the GraphQL schema yet.

**Learning Goals:**
- Use Claude Code to navigate unfamiliar resolver code
- Trace data flow from schema to backing service
- Understand dataloader patterns in practice
- Practice test-driven development for new fields

**Time:** 15 minutes including Q&A

## Scenario D: CI/PR Triage with codegen-drift Error

**Context:** You pushed a PR that adds a new mutation to the schema. CI fails with a check called "codegen-check" showing git working tree is dirty. The error message is cryptic. You need to understand what went wrong, fix it, and get the PR green.

**Learning Goals:**
- Use Claude Code to interpret CI logs
- Understand gqlgen's generated code and why it matters
- Learn the "schema + generated code" commit pattern
- Explore new April 2026 commands: `/autofix-pr` and `/ultrareview`

**Time:** 15 minutes including Q&A

---

### Demo Script: Step-by-Step

**SETUP (Pre-Demo):**
- Create a branch with a schema change but DON'T run codegen
- Push to GitHub, let CI fail
- Pull up the failing PR in browser (show red X on checks)
- Open terminal in repo root: `claude`

---

**STEP 1: Understanding the CI Failure (2 minutes)**

**Say to audience:**  
"Our PR is failing CI. The check is called 'codegen-check'. Let's ask Claude to explain what's happening."

**Prompt to Claude:**
```
My PR is failing the "codegen-check" CI step. Can you look at the CI log 
and explain what's wrong and how to fix it?
```

**Expected Claude Behavior:**
- Runs `gh pr view --json statusCheckRollup` or similar to get CI status
- Runs `gh pr checks` to see failing check details
- Reads the log output from the failing check
- Analyzes the error message

**Sample CI Log (What Claude Will See):**
```
Run codegen check
  go run github.com/99designs/gqlgen generate
  git diff --exit-code
  
Changes detected in generated files:
 M graph/generated/generated.go
 M graph/schema.resolvers.go

Error: Generated code is out of sync with schema.
This usually means you edited schema.graphql but didn't run codegen.

Fix: 
  go run github.com/99designs/gqlgen generate
  git add graph/generated/ graph/schema.resolvers.go
  git commit --amend
  git push --force
```

**Expected Claude Output:**
```
The codegen-check is failing because your schema.graphql was updated 
but the generated code wasn't regenerated and committed.

gqlgen generates Go code from your GraphQL schema. When the schema changes, 
the generated code must be updated and committed together.

To fix:
1. Run: go run github.com/99designs/gqlgen generate
2. Commit the generated files
3. Push the fix
```

**What Could Go Wrong:**
- CI log might not be accessible via `gh` CLI (permissions issue)
- Claude might not have `gh` CLI installed
- **Fallback:** Paste the CI log directly into the conversation

**Point Out to Audience:**  
"This is a common mistake in gqlgen projects: forgetting to commit generated code. The CI check catches this before it breaks production."

**STEP 5: Understanding the CI Check (3 minutes)**

**Say to audience:**  
"Let's look at the actual CI workflow to understand how the codegen-check works. This will help you write similar checks for your own projects."

**Prompt to Claude:**
```
Show me the CI workflow file that runs the codegen-check. 
Explain how it works and why it's useful.
```

**Expected Claude Behavior:**
- Reads `.github/workflows/test.yml` or similar
- Shows the codegen-check step
- Explains the git diff check

**Sample Workflow (What Claude Will Show):**
```yaml
name: Test

on: [push, pull_request]

jobs:
  codegen-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.22'
      
      - name: Generate code
        run: go run github.com/99designs/gqlgen generate
      
      - name: Check for drift
        run: |
          if ! git diff --exit-code; then
            echo "Generated code is out of sync with schema."
            echo "Run: go run github.com/99designs/gqlgen generate"
            exit 1
          fi
```

**Claude's Explanation:**
```
The codegen-check works like this:

1. Checkout code (including your schema changes)
2. Run gqlgen generate (produces new generated code)
3. Check if working tree is dirty (git diff --exit-code)
4. If dirty, fail the build

Why this matters:
- Prevents schema/code drift
- Catches forgotten codegen runs
- Ensures all developers commit generated code consistently

This pattern is common in codegen-heavy projects (protobuf, OpenAPI, GraphQL).
```

**Point Out to Audience:**  
"This CI pattern is something you should implement in all gqlgen projects. It's a safety net for the most common mistake: forgetting to run codegen."

**Comparison of Review Commands:**

| Command | Speed | Depth | Cost | When to Use |
|---------|-------|-------|------|-------------|
| `/review` | Fast (< 1 min) | Single-pass | Free | Quick sanity check, every PR |
| `/ultrareview` | Slow (5-10 min) | Multi-agent, verified findings | $5-$20 after free tier | Critical PRs, pre-merge |
| `/security-review` | Fast (< 2 min) | Security-focused | Free | Security-sensitive changes |

**Common questions:**
- Q: "Can `/autofix-pr` break things?"  
  A: Yes, if your repo has comment-based automation (Atlantis, Terraform Cloud). Know your hooks. Also, Claude might misinterpret complex CI failures.

- Q: "Is `/ultrareview` worth the cost?"  
  A: For critical code paths, security-sensitive changes, or major refactors, absolutely. For minor fixes, use `/review`.

- Q: "What if I don't have `gh` CLI installed?"  
  A: `/autofix-pr` requires it. Install with `brew install gh` (macOS) or see https://cli.github.com/

### Day-1 Advice for Client Team

**For engineers onboarding to the gqlgen subgraph project:**

**Week 1 priorities:**
1. Set up CLAUDE.md with schema location, codegen command, resolver patterns, and CI check names
2. Document your dataloader conventions if you use them
3. Run `claude` and try: "explain how our Product resolver fetches data"
4. Before first PR: practice the full workflow (schema edit, codegen, implementation, test, commit)

**Common pitfalls to avoid:**
- Editing generated files manually (they get overwritten)
- Committing schema changes without generated code
- Skipping codegen in CI (add the check if missing)
- Not using dataloaders when resolving list fields

**Commands to bookmark:**
- `/review` - quick PR review before pushing
- `/ultrareview` - deep review before merging critical changes
- `/autofix-pr` - autonomous PR maintenance (use cautiously)
- `/help` - when stuck, start here

**CLAUDE.md is your superpower:**
The single most important file for Claude Code productivity. Spend 30 minutes on day 1 documenting your patterns, and Claude will follow them consistently.

**When Claude gets it wrong:**
- Check CLAUDE.md first - is the pattern documented?
- Read existing code - does it actually follow the pattern consistently?
- Iterate with follow-up prompts: "I think this will cause N+1 queries, can you use a dataloader?"

**Integration with existing tools:**
- Claude works alongside your IDE, not instead of it
- Use GitHub Copilot for line-level autocomplete, Claude Code for multi-file workflows
- CI integration: add `claude ultrareview` to your GitHub Actions for automated deep reviews
