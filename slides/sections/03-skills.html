Skills
Writing and evaluating them

Two halves: how to write one, and how to know it works.

Part A · What a skill is

Frontmatter plus markdown

  • Lives in ~/.claude/skills/<name>.md (user) or .claude/skills/ (project).
  • Invoked by slash command (explicit) or matched by description (implicit).
  • Body is a plain markdown document. No DSL, no sandbox.
skills-lab/01-minimal/SKILL.md
---
name: commit-message
description: Use when the user asks for a commit message for staged changes. Reads git diff --cached and produces a short conventional-commits summary.
---

Read the staged diff. Summarize in one line using conventional commits.
Body stays under 200 lines. Reference the diff directly; do not restate it.
Authoring happens CapTech-side

90 seconds. Point out: frontmatter + body. That's all a skill is.

Part B · The counterintuitive rule

The description is a behavior lever, not metadata.

If the description summarizes the workflow, Claude follows the description and skips the skill body entirely.

Superpowers proved this empirically. A description reading "code review between tasks" caused Claude to do one review despite the body mandating two. obra/superpowers, writing-skills findings

This is the surprising bit that gets people talking. Slow down. Let the quote land.

The rule

Descriptions describe when to use the skill.

Third-person triggers. Symptoms. "Use when..." sentences.

Never what the skill does.

The body does that.

Read the rule twice. Once fast, once slow.

Part C · How to know a skill works

The community has no formal framework. Here is a minimal one.

  1. Write three golden tasks with plain-English expected-behavior bullets before writing the skill.
  2. Run them without the skill in a fresh session. Capture transcripts. RED baseline.
  3. Write the skill to target the baseline failures.
  4. Re-run the golden tasks. Require GREEN on the previously-failing bullets.
  5. Pressure-test: run each golden task 3 times to check for nondeterminism.

3 minutes on this slide. This is the part people came for.

Mention promptfoo as adjacent — runs a skill body as a regression harness, but cannot test whether Claude chooses to load the skill.

What the harness looks like on disk

skills-lab/03-eval-harness/

test-prompts.json
{
  "id": "commit-message-01",
  "prompt": "Write a commit message for the staged changes.",
  "expected": "one-line conventional commit, type prefix, under 72 chars",
  "tests": [
    { "contains_regex": "^(feat|fix|chore|refactor|docs|test)(\\([^)]+\\))?: " },
    { "max_length_first_line": 72 }
  ]
}

Four fields: id, prompt, expected, tests. Modeled on huashu-design's pattern.

Do not deep-dive. Point out the shape, move on.

Part D · A working example

The chunked-write pattern

~/.claude/skills/graphqlstagereport.md
---
name: graphqlstagereport
description: Use when producing a long staged report whose total length
  risks hitting the 4096 output-token cap mid-response. Symptoms:
  truncation, "..." endings, or files cut off.
---

Produce each section as its own Write call. Stop between sections.
Never combine sections in a single output. Cap each file at ~2500 tokens.

Community-evolved. Not in Anthropic's docs. Dodges the CLAUDE_CODE_MAX_OUTPUT_TOKENS=4096 cap.
