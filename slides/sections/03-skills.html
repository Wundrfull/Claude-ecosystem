What it actually is

A skill is a directory with SKILL.md — nothing more.

~/.claude/skills/commit-message/
commit-message/
└── SKILL.md    # required entrypoint
commit-message/SKILL.md
---
description: Use when the user asks for a commit message for
  staged changes. Reads git diff --cached and produces a
  short conventional-commits summary.
---

Read the staged diff. Summarize in one line using
conventional commits. Reference the diff; don't restate it.

Directory name becomes the slash-command. Drop this in, type /commit-message, done.

60 seconds. Reframe from the existing mental model: "You do not need a plugin, you do not need a manifest, you do not need to register anything. A folder with a markdown file. That is the entire contract."

Live change detection: save the file, the skill is live in the next turn.

Long skills are free until you use them. A 2,000-line skill costs almost nothing until Claude invokes it.

90 seconds. This is the concept to land. Why can you have 30 skills installed and not pay a context penalty? Because only the names and one-line descriptions are always there. The body loads on invoke.

Corollary: your description IS the activation lever. If it's vague, Claude will not pick your skill when it matters.

The fields that matter

Only description is recommended. The rest tune behavior.

description What it does AND when to use it. First 1,536 chars are the whole index entry. Front-load the "use when" trigger.
disable-model-invocation: true Manual-only. Use for side-effect workflows like /deploy, /commit, /send-slack.
allowed-tools Pre-approve tools while the skill is active. Bash(git add *) Bash(git commit *)
context: fork Run the skill body as the prompt to an isolated subagent. Pair with agent:.
agent: Explore | Plan | general-purpose Which subagent type executes the forked context. Explore is read-only; Plan is planning-focused.
paths Glob patterns. Skill auto-loads only when Claude touches matching files.

90 seconds. Walk the table top to bottom. The two that matter most for this team today: disable-model-invocation for anything with side effects, and allowed-tools to stop the approval-prompt spam.

Ship your first skill tonight

Five steps. Ten minutes.

  1. mkdir -p ~/.claude/skills/explain-code
  2. Create SKILL.md — frontmatter plus body.
  3. Write the description as "Use when..." — triggers and symptoms, not what it does.
  4. Save. Live change detection picks it up without restarting.
  5. Invoke with /explain-code — or let Claude match it from your prompt.
~/.claude/skills/explain-code/SKILL.md
---
description: Explains code with diagrams and
  analogies. Use when the user asks
  "how does this work" or is onboarding
  to an unfamiliar file.
---

When explaining code:
1. Start with an analogy from everyday life.
2. Draw an ASCII diagram of the flow.
3. Walk through the code step by step.
4. Highlight one gotcha or misconception.

120 seconds. This is the "do it Monday" slide. Walk the left column as a checklist. Show the right as the actual artifact.

The `.claude/skills/` variant (project-level) goes in the repo and ships with the team. The `~/.claude/skills/` variant (personal) is just for you.

Two knobs that extend skills · 60s aside

Where subagents and hooks fit

Subagents

Add context: fork + agent: Explore to your SKILL.md. The skill body becomes the task; an isolated context window does the work.

Use for: research, code review, anything that would pollute your main conversation.

Hooks

Shell commands that run on tool events. Deterministic, unlike CLAUDE.md instructions. Configured in .claude/settings.json.

Use for: block force-push without a flag, run lint after every edit, enforce what CLAUDE.md only requests.

Mental model: Skills are the playbook. Subagents are where it can run. Hooks are the guarantee.

60 seconds flat. Do not deep-dive. The job here is name recognition so "subagent" and "hook" are not foreign words when they come up later on the job.

The one rule that breaks most skills

Descriptions say when, never what.

Descriptions describe when to use the skill.

Third-person triggers. Symptoms. "Use when the user asks..."

Never describe what the skill does.

That's the body's job.

If the description summarizes the workflow, Claude follows the description and skips the body entirely. Proven empirically — the Superpowers "code review between tasks" bug.

60 seconds. Read the rulebox twice — once fast, once slow. End on the concrete failure mode: if your description says "do X then Y," Claude may do just X and never read the body.
